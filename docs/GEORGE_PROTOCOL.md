# George Protocol — The Last Reboot

## Scope and safety

George Protocol is an in-game round outcome implemented by the authoritative `Room`. It does not read or use host credentials, invoke operating-system commands, call cloud administration APIs, or reboot a real server. The six-digit value is generated by the room with Web Crypto and exists only as a round-scoped game credential.

## Killstreak and credential lifecycle

`Player.georgeStreak` counts confirmed lethal player eliminations in one life. The count is advanced after the existing server hit/execution resolution, not from client kill reports. Ordinary lethal disc/FRC/gold hits, ordinary executions, completed THE BOOMERANG eliminations, and the existing disconnected execution-target settlement path feed the same idempotent George award helper. NPC/security eliminations do not award progress; a lethal event prevented by revive armor does not award progress. A real death revokes the victim's code and resets their streak; revive armor preserves it. New rounds reset it. A live authenticated player's round standing restores it after a short reconnect; the credential is private to the owner's welcome/message and is omitted from public summaries.

The room generates a unique six-digit code at 10/10. The owner can reveal it from the task card with `P` or the on-screen control. The credential is bound to the account, room round, and credential ID; login additionally requires a living player at the terminal. It is revoked on death, round end, successful reboot start, or room reset. Credentials and George state are in room memory, not a separately migrated durable database; a recreated/evicted room safely starts a fresh room state rather than replaying a reboot result.

## M103 authored room and placement evidence

The source-derived room record identifies M103 as 创客空间 / MakerSpace. Its inferred polygon contains the selected point and the existing FRC pickup at `[-44.24, 0.2, 25.54]`. The source does not identify a server closet or surveyed server location. The compact three-wall alcove, server rack and console are therefore `GAMEPLAY_AUTHORED`, not campus-source geometry. The authored room origin is `[-42.2, 25.54]`; the shared interaction anchor is `[-40.9, 0.92, 25.54]`, in front of the console collision boxes. The browser test checks the interaction prompt at this anchor. It does not establish that the real building contains this room.

The local scene props have static box collisions. The service has no PlayCanvas/Ammo world or line-of-sight geometry. Server access uses the current room pose, an X/Z radius and a vertical tolerance. Since the existing movement protocol is client-reported, this is a gameplay proximity check, not authoritative collision or anti-cheat proof; wall occlusion and spoofed movement remain limitations.

## Terminal and room state machine

The terminal is opened with `E`; the password is entered in a modal input context. `Enter` authenticates and advances the visible restart/confirm controls. Opening the terminal disables local movement/throw input and releases pointer lock for UI access. The main loop recognizes this as terminal focus and continues room/physics time so the operator remains vulnerable. Reacquiring pointer lock resumes local controls. `Escape` closes the console.

The server validates owner, six-digit code, alive/playing status, current round, terminal distance, and cutscene/ceremony/finisher exclusivity. A short request-ID cache prevents replays, and login attempts have a 500 ms minimum interval. The code is consumed only after reboot start succeeds.

`idle → pending → resolved(aborted | shutdown)` is the reboot lifecycle. Pending lasts 10 seconds on the server room clock. Natural round-end checks and new global finishers are blocked during the pending phase; player combat continues. The round deadline is extended by the pending duration if the reboot is aborted. The initiator's death/disconnect does not cancel a pending reboot while other players remain. The room's existing empty-room grace/reset clears the reboot state if the room empties or is recreated, preventing a stale second settlement.

Non-initiators must remain alive and at the terminal while sending hold heartbeats. The server checks terminal proximity, alive state, initiator identity, lease freshness, and the two-second duration before resolving the abort. Leaving, dying, disconnecting, or releasing the hold cancels the attempt. If the deadline wins, the server broadcasts a simulated shutdown and settles `george-reboot` once after the short black-screen beat. The initiator wins even if disconnected; the result adds no synthetic kills/deaths and uses the existing once-only round settlement path.

## Network and compatibility

Protocol version is 16. The server sends absolute private progress, owner-only credential messages, a public credential-leak alert with no code, and an authoritative reboot phase/deadline. Welcome contains the joining player's George state plus the public room reboot state. Old protocol-15 clients are rejected by the existing exact-version gate; they cannot safely join a George-enabled room because they do not render the warning/blackout/result. Release therefore requires a coordinated client and server rollout in isolated staging before any production deployment.

The local browser E2E fixture endpoint `/api/__test/george-streak` is available only when `COMBAT_TEST=1`, requires a signed-in account, and only prepares that account at 9/10. It neither creates a credential nor forces a win. It is not available in production configuration.

## Known limitations

- The server validates proximity from reported poses; it does not prove collision support, path reachability, or line of sight.
- The exact MakerSpace server-room placement is authored; source geometry does not verify a closet at this location.
- Credential/reboot data is room-memory state and is not restored across a destroyed room instance. The safe behavior is a fresh round with no replayed result.
- The password reveal shortcut (`P`) and terminal/interaction shortcut (`E`) are direct bindings because the latest performance baseline does not include the separate customizable-controls feature branch.
- Fan motion and status lights are local scene effects. A dedicated fan hum and a bespoke reward sound were not added; the existing blackout cue is reused for the breach/shutdown warning.
- The server model and paths have not been visually accepted by a human player on the real campus asset.

## Rollback

Revert the George feature commits on the feature branch. Because the protocol is versioned and exact-version gated, do not publish a protocol-16 client while leaving a protocol-15 Worker active (or vice versa). No database schema, player account data, production room, or operating-system service is changed by this feature.
